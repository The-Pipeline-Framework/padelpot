# PadelPot

**Padel matchmaking.**

A local, open-source padel coordination experiment for Hacktoberfest 2026 — Touch Grass. Four fictional owners talk privately with personal agents. Gemma proposes and negotiates a doubles match; deterministic rules protect private fields, enforce capacity and wait for each owner's explicit approval. No court is booked.

## Run

Requires Java 21 and Python 3 for the optional evidence runner. The included Maven wrapper downloads released dependencies. TPF **26.9.4**, Quarkus **3.39.2**.

Default Gemma through OpenRouter:

```sh
export OPENROUTER_API_KEY='your-key'
./scripts/run.sh
```

Open [the chat simulator](http://127.0.0.1:8080). No Meta account, messaging service or local GPU is required. Routing requires eligible zero-data-retention providers, data collection denied, no provider fallback and supported structured output. Missing credentials or unavailable routing fails closed. The remote path is configured but was not exercised in the development environment because no key was supplied.

Optional local inference using the existing TPF OpenAI-compatible integration:

```sh
ollama pull gemma4:12b-it-qat
./scripts/run.sh ollama
```

Ollama must already be running on localhost:11434. This is an explicit provider selection; it never happens automatically. Its model name is inspectable in `app/src/main/resources/pipeline.ollama.yaml`. Local inference needs sufficient memory; use the default remote option if you do not want to run a model locally.

## Try the conversations

1. As **Alba**, ask to open a competitive match on Thursday at 19:00. Approve her own participation.
2. Switch to **Nico**, ask to find a match. He prefers 20:00 and must explicitly allow a 19:00 compromise. Approve participation after negotiation.
3. Ask **Luz** and **Teo** to find the match and approve their tentative agreements. Teo can play either side.
4. Once all four approve, simulate the match and give feedback. Review the proposed inference before saving it.

The agents' actions and outcomes are generated by the selected Gemma model. They may decline, counter or run out of turns. A model failure never approves a place. Synthetic human choices in the automated runner are fixtures; interactive approvals require clicking in the selected owner's private chat.

“My preferences” shows provenance and disclosure status, supports deletion, blocking and intent cancellation, and offers fresh conversational onboarding. State one preference at a time, for example “My level is intermediate”, then review the proposed update. The agent activity panel shows permitted peer exchanges, privacy decisions, approval checkpoints and native execution status. Owner switching is a **demo simulation, not authentication**.

## Verify and reproduce

```sh
./scripts/test.sh                         # deterministic business and TPF topology tests
./scripts/reproduce.sh ollama             # fresh real Gemma E2E; leaves UI running
# Or use ./scripts/reproduce.sh with OPENROUTER_API_KEY set.
```

The named `fourOwnersNegotiateAndLearn` scenario verifies four explicit participation approvals, valid doubles capacity, Nico's permission, approved inferred learning, and exactly **five roots**. Human replies resume those roots. `scripts/e2e.py` can also run against a fresh already-running server; the replay directory must be empty. It rejects the fixture provider unless explicitly requested with `--allow-fixture`.

Native TPF replay is written to `output/tpf-replay`. The evidence runner exports `output/evidence/demo-execution-dataset.json`, unchanged native documents and five root groupings. TPF 26.9.4 exports execution **segments** and a shared Await control document, so native file count equals roots + human resumes + one control document. Native events/topology are preserved; the runner asserts both that count and the native Await root IDs.

Generated state, recordings and evidence are local files excluded from Git. See [scenario instructions](docs/scenarios.md).

## Architecture and boundaries

One application process, four logical agents, one inference at a time. Versioned personas and the organizer's match aggregate are application-owned JSON state. TPF owns typed contracts, Queries, Commands, nested recursion, correlation, regular-step Await completion and native execution evidence. See [architecture](docs/architecture.md), [privacy and information leaving the app](docs/privacy.md), and [implementation plan](docs/implementation-plan.md).

This demonstration has no production authentication, encryption, independent-device isolation, booking, public reputation or production recovery. Persona data persists locally; pending TPF executions and interactions use memory and are lost on restart. Broad Barcelona areas and 19:00/20:00 slots keep the experiment bounded. One clarification plus a final review is supported; further ambiguity requires a new request. Negative feedback remains private and never becomes a public score. A local blocked-owner rule is authoritative.

An intermittent recursive execution error was observed in one live run; the same scenario passed after restarting the process. It remains unresolved and is documented in the architecture. A failed recording is reported as a failure, with no silent model fallback. See [production follow-up](docs/productionization.md).

Use only fictional data. The current owner message and minimal preferences reach the configured inference provider; remote inference is not fully private. Deleting a current persona field does not erase historical chat or exported evidence.

Apache-2.0. New application work; TPF and its released connectors are dependencies. See [contributing](CONTRIBUTING.md) for scoped Hacktoberfest work.
