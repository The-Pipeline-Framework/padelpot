# PadelPot

**Padel matchmaking.**

A local, open-source padel coordination experiment for Hacktoberfest 2026 — Touch Grass. Four fictional owners talk privately with personal agents. Gemma proposes and negotiates a doubles match; deterministic rules protect private fields, enforce capacity and wait for each owner's explicit approval. No court is booked.

![PadelPot chat showing Alba's match request and explicit participation approval](docs/images/padelpot-updated.jpg)

## Run

Requires Java 21 and Python 3 for the optional evidence runner. The included Maven wrapper downloads dependencies. TPF **26.10.1-SNAPSHOT**, Quarkus **3.39.2**. The snapshot includes the [recursive parent-context fix](https://github.com/The-Pipeline-Framework/pipelineframework-runtime/pull/44) needed by this demo; see the [live verification](docs/live-verification.md) for the exact tested runtime build.

Default Gemma 4 (`google/gemma-4-26b-a4b-it`) through OpenRouter:

```sh
export OPENROUTER_API_KEY='your-key'
./scripts/run.sh
```

Open [the chat simulator](http://127.0.0.1:8080). No Meta account, messaging service or local GPU is required. Routing requires eligible zero-data-retention providers, data collection denied, no provider fallback and supported structured output. Missing credentials or unavailable routing fails closed. Real Gemma 4/OpenRouter verification passed through the actual web chat and the complete API scenario on 11 October 2026. Business-rule tests use explicit fixtures; they remain separate from this live proof.

Optional local inference using the existing TPF OpenAI-compatible integration:

```sh
ollama pull gemma4:12b-it-qat
./scripts/run.sh ollama
```

Ollama must already be running on localhost:11434. This is an explicit provider selection; it never happens automatically. Its model name is inspectable in `app/src/main/resources/pipeline.ollama.yaml`. Local inference needs sufficient memory; use the default remote option if you do not want to run a model locally.

## Try the conversations

1. As **Alba**, ask to open a competitive match on Thursday at 19:00. Approve her own participation.
2. Switch to **Nico**, ask to find a match. He prefers 20:00 and must explicitly allow a 19:00 compromise. Approve participation after negotiation.
3. Ask **Luz** and **Teo** to find the match and approve their tentative agreements. Teo can play either side.
4. Once all four approve, simulate the match and give feedback. Review the proposed inference before saving it.

The match card shows two teams, each with a left and a right place. Owners can declare both sides OK, a soft left/right preference, or a strong preference for one side only. Every participation review names the team and side. See the [padel rules](docs/padel-specs.md).

The agents' actions and outcomes are generated by the selected Gemma model. They may decline, counter or run out of turns. A model failure never approves a place. Synthetic human choices in the automated runner are fixtures; interactive approvals require an explicit button in the selected owner's private chat.

Use the same composer for conversation and matchmaking. A new message starts one execution: PadelPot hydrates authorised owner history and permitted player facts through a captured Query, then makes one ChatAgent decision. It can reply, use the read-only court-guide Query and synthesise a reply, or propose a typed owner action. PadelPot validates and applies an action through its own Command; match negotiation still uses independent player-specific agents. Ask “Where is the court?” to exercise the Query path. While a participation review is pending, a chat message starts a new owner conversation with that review in its authorised context. Discussion leaves the review open. To change the offer, enter the proposed terms in the review's Counter control. Approve, Decline and Counter are explicit controls that resume native Await; conversation never implies approval. The UI’s owner selector remains a demo simulation, not authentication.

"My preferences" shows provenance and disclosure status, supports deletion, blocking and intent cancellation, and offers fresh conversational onboarding. The chat box answers a pending conversational question directly; during a participation or permission review it lets you discuss the offer without changing it. Use the review's explicit Approve, Decline or Counter controls to act on it. A permission review also accepts an explicit clarification; “I'm flexible” in that control allows only the named time or style for this request, never participation or a saved preference. State one preference at a time, for example “My level is intermediate”, then review the proposed update. The agent activity panel shows model reasoning, permitted peer exchanges, privacy decisions, approval checkpoints and native execution status. Owner switching is a **demo simulation, not authentication**.

The tested TPF runtime exports execution **segments** and a shared Await control document, so native file count equals roots + human resumes + one control document. Native events/topology are preserved; the runner asserts both that count and the native Await root IDs.

Generated state, recordings and evidence are local files excluded from Git. See [scenario instructions](docs/scenarios.md).

## Architecture and boundaries

**Typed Core / Smart Shell.** TPF is inspired by [Functional Core / Imperative Shell (FCIS)](https://pipelineframework.org/architecture/fcis). Its agentic capabilities extend that separation: typed contracts and application rules define the decisions, while the framework coordinates model Queries, Command effects, bounded execution and human interaction. In PadelPot, Gemma proposes; deterministic rules and owner approvals control what becomes a commitment. The [architecture diagrams](docs/architecture.md) show how those responsibilities fit together.

One application process, four logical agents, concurrent owner requests and one inference at a time. Approved `Owner`, `Match` and conversation-turn values cross typed pipeline boundaries; TPF's native persistence aspect maps them to a local H2 database. The application owns business rules, aggregate versions, conversation scope and retention, while TPF owns persistence execution, Queries, Commands, nested recursion, correlation, regular-step Await completion and native evidence. See [architecture](docs/architecture.md), [privacy and information leaving the app](docs/privacy.md), and [implementation plan](docs/implementation-plan.md).

This demonstration has no production authentication, encryption, independent-device isolation, booking, public reputation or production recovery. Approved aggregate versions and accepted owner/agent conversation turns persist in `output/runtime/padelpot.mv.db`; temporary intents and pending TPF executions/interactions still use memory and are lost on restart. Startup restores the latest 99 saved turns per owner into the bounded chat view. The `persona.snapshot` Query reads at most 100 earlier turns scoped by tenant and acting owner, then uses the portable conversation context assembler to select the newest turns within a conservative input budget. Its captured output supplies the model's explicit `recentHistory` input in chronological order. An oversized turn without an owned reference is omitted, and a current owner message that cannot fit fails the Query. The application retains stored turns until **Reset fixtures** or the explicit `DELETE /api/owners/{owner}/history` Command. That demo endpoint uses the selected fictional owner ID, not a production identity check. Match identifiers and the match selector distinguish saved opportunities. The old JSON state file is no longer read and is left untouched. Broad Barcelona areas and 19:00/20:00 slots keep the experiment bounded. One clarification plus a final review is supported; further ambiguity requires a new request. Negative feedback remains private and never becomes a public score. A local blocked-owner rule is authoritative.

The unified owner path uses ChatAgent’s carried `ChatState` and independent state and model-context limits. PadelPot hydrates accepted history once before the decision, binds the model, public court-guide Query and one finite owner-action Command contract, then validates the Block result. A natural reply is accepted through an application Command. A handoff is only a proposal: the Block never executes the owner-action Command, and PadelPot checks scope and domain terms before admission. Native persistence observes accepted turns. Match actions enter the established policy, peer-agent negotiation and Await boundaries. A client-supplied `ChatState` would need application authorisation before use; this demo constructs it server-side.

PadelPot tells the model to keep replies within its fictional padel scope, answer each part of a mixed message, and say when it cannot arrange transport, disclose another player, book a real court or make an external commitment. Callable inputs are finite typed contracts; the application rechecks owner scope and business terms before any effect. A pending-review counter is an explicit owner control, so a model cannot infer a counter from free text. Input and carried context are bounded. These measures limit off-topic use and unauthorized effects, but a prompt cannot guarantee that every natural-language reply stays on topic. The demo has no user authentication or per-user inference quota; a production deployment needs both at admission.

History erasure removes turns present when its Command runs. An in-flight request can emit another turn afterwards, so this demo does not provide a complete privacy-erasure guarantee while requests remain active. Production use needs authenticated owner identity and a policy for draining or fencing in-flight requests before erasure completes.

To exercise history across a real process boundary with an isolated fixture database, run `./mvnw -q -Pfixture -DskipTests package` followed by `python3 scripts/history-restart-smoke.py`. The smoke check starts the packaged app twice, verifies the saved turn after restart, and asks a follow-up using the prior text.

For a real-model context check, start a fresh disposable PadelPot server using OpenRouter or Ollama, then run `python3 scripts/context-real-smoke.py --base http://127.0.0.1:8080`. The script sends an initial time, an explicit correction with a reason, and a later recall question in separate roots. It requires natural replies and the final answer to use the correction and reason. The fixture model does not satisfy this check; a model that proposes an action or an Await review for these statements fails the smoke check.

Persistence failures fail the root; in-memory working changes are not automatically rolled back. This is a single-process capacity authority, with no cross-process transaction guarantee. Live testing reproduced the recursive execution failure on TPF 26.9.4; sequential processing did not resolve it. The app now uses the published runtime fix in 26.10.1-SNAPSHOT, verified with real Gemma and the regression suite. Snapshots can change, and successful recordings do not guarantee every future model outcome. Failed recordings remain failures, with no silent model fallback. See [live verification](docs/live-verification.md) and [production follow-up](docs/productionization.md).

Use only fictional data. The current request, selected earlier turns, pending conversational question, correlated answer and minimal preferences reach the configured inference provider; remote inference is not fully private. Deleting a current persona field does not erase historical chat or exported evidence. Erasing saved conversation history does not remove exported replay files or provider-side data.
